# 后记

写这本书的念头，不是某一天突然出现的。

读博士时，我做智能交通研究，习惯从模型和数据出发看问题。进入产业、真正参与系统建设之后，我才逐渐发现：同一个“周期”，在论文里是一个变量，在方案库里是一个字段，在设备上却是一段真实流逝的时间；同一个“流量”，在仿真里是一条曲线，在现场却可能是缺失的、延迟的，或者经过补全和修正的数据。中间每一次转换，都可能改变最终的结论。

后来，随着项目做得越来越多，现场跑得越来越多，我逐渐意识到，相比再多一个算法，这个行业更需要能够在交通语言和软件语言之间来回翻译、并把两者真正连接起来的人。

交通工程师说“这个周期太短”，软件工程师听到的可能只是“改一个字段”；软件工程师说“下发成功”，交通工程师理解的却可能是“路口已经按照新方案运行”。两边都没有错，只是各自看到的，并不是同一层事实。

学生和刚入行的工程师，往往还会卡在更前面。他们不知道一个真实的信号控制项目究竟从哪里开始：数据怎么进来，方案怎么算出来，控制命令怎么发出去，执行失败又该怎么查。仿真软件可以给他们一个漂亮的结果，却很难让他们真正看到这些结果背后的工程过程。这本书想补上的，就是这一段。

写这本书时，我做了几个取舍。

第一，先讲系统，再讲代码。代码是证据，不是目录。先理解一个路口、一个周期、一次方案下发在工程上究竟意味着什么，再去看某段 Python 或 Java 代码为什么这样写。

第二，把生产代码里的缺陷保留下来。这不是为了展示“系统有多差”，而是因为真实系统并不总是在理想条件下设计出来的，而是在各种约束、历史和妥协中逐渐生长起来的。保留这些问题，是为了让读者看到真实系统中的缺陷如何产生、如何被发现，以及应该怎样验证和修正，而不是把它们当作可以照搬的实现。看懂一个系统为什么会出错，往往比记住一个漂亮的实现更有价值。

第三，把 SignalLab 做成一个可运行的教学系统。书中的结论，应该能自己跑一遍，改一个参数，看结果如何变化，甚至观察它在什么条件下会出错。不能运行、不能验证的“工程书”，很容易又退回到公式和框图。

第四，不追求覆盖所有主题。感应控制、行人相位、公交优先、区域自适应控制等，都值得深入讨论，也都有各自复杂的工程问题。一本书装不下所有内容，硬要装进去，只会让每个主题都讲得不够深入。

AI 时代，让知识组织和代码生成变得容易，也让真正的工程判断更加珍贵。AI 可以很快地组织跨学科知识，生成一份看起来完整的方案，甚至给出一套逻辑自洽的代码。但它不能替工程师判断这些结果是否适用于真实场景，也不能替工程师承担工程后果。最终仍然需要有人追问：这个数从哪里来？使用的是不是正确的版本？这条约束有没有被绕过？所谓的“成功”，究竟只是设备接受了命令，还是路口真的按照预期发生了变化？

工程把关人的门槛并没有因为 AI 而降低。我们不仅要看懂 AI 给出的东西，还要知道它在什么条件下成立，又会在哪里失效。

所以，这本书真正想留下的，不是某一个公式，也不是某一段代码，而是三个值得反复追问的问题：

**时间以谁为准？状态存在哪里？证据是什么？**

将来，无论面对的是另一个城市、另一套平台，还是另一家公司的系统，这三个问题依然成立。

如果这本书能让一个学生早一点看到真实系统的样子，让一个刚入行的工程师少走几年弯路，让一个做算法的人在方案下发之后多问一句“设备真的执行了吗”，那么，这本书的意义或许仅止于此。

郭海锋，2026年11月，杭州
