# 第 8 章 实时信号状态与信号机接口

第 7 章结尾留下了一个问题：系统怎么知道当前方案是否真正在执行。把它放进一个晚高峰的现场：设想 17:00 整，中心向 40 个路口批量下发新方案，回执逐条“成功”；五分钟后值守热线接到反映，某路口仍按旧配时放车。方案没有错、下发没有断、回执没有报错，问题出在某一环，但不在算法本身：可能是设备尚未完成切换，可能被现场人工接管，可能是状态在网络里迟到，也可能同一周期被重复推送。自适应控制、效果评价和故障处理，都依赖“设备正在执行什么”；这个判断不准，决策就会偏。

领域模型中的方案回答“计划执行什么”，实时信号状态回答“设备正在执行什么”——两者可能不同。本章要把这个缺口补上：先给出实时状态的最小字段和四个时间坐标，再讨论控制模式对字段的约束、时间的合法边界与过期判断；随后沿数据链路向下：厂商适配、状态事件与消息链路，最后把命令与观测放进同一张联合视图。

## 8.1 实时状态的最小字段

WaySense 的实时阶段对象包含：

- 路口和设备标识
- 周期开始、结束和当前已走秒数
- 当前阶段和刚结束阶段
- 当前周期、方案编号
- 控制模式与控制级别
- 相位差和锁定状态
- 数据来源、推送时间
- 批次和操作序列

这些字段不仅是展示信息，也决定算法是否可以判断状态。

例如，只知道 `cycleTime=90`，却不知道阶段开始时间和已运行秒数，就无法计算当前绿窗还剩多少；只知道当前阶段，却不知道控制模式，就可能把人工控制误认为自动控制。

概念状态可以表示为：

```json
{
  "siteId": "S1",
  "observedAt": "2026-11-10T08:15:03+08:00",
  "cycleSeconds": 90,
  "elapsedSeconds": 35,
  "controlMode": "fixed",
  "currentStageId": "B",
  "source": "vendor-adapter",
  "batchId": "batch-42"
}
```

生产字段可能更多，但这个最小结构已经能够支持状态校验、过期判断和命令匹配。

### 8.1.1 四个时间坐标

实时状态至少涉及四个时间：

具体见表 8-1。
表 8-1 四个时间坐标
| 时间 | 含义 | 典型问题 |
|---|---|---|
| `device_time` | 信号机采集时的时钟 | 设备时钟漂移 |
| `event_time` | 状态事件代表的控制时刻 | 厂商按灯组推送 |
| `received_at` | 平台网关收到消息的时间 | 网络延迟 |
| `processed_at` | 流任务完成计算的时间 | 重试和积压 |

如果只保存 `received_at`，17:00:00 开始执行的某个阶段可能在 17:00:25 才被平台看到，算法却会认为它是 17:00:25 的新状态。用设备时间处理乱序，用接收时间监控链路延迟，用处理时间观察计算积压，三者不能互换。

设备时钟也可能回拨。一个合理的事件排序键通常是：

```text
(site_id, device_id, event_time, vendor_sequence)
```

当 `event_time` 相同或不可信时，`vendor_sequence` 用来确定同设备事件顺序。缺少设备序列号时，系统只能做保守更新，并把“顺序不确定”写进状态。

### 8.1.2 周期已走时间

对正常周期，`cycleSeconds=90`、`elapsedSeconds=35` 的含义是周期已走过 35 秒，不是阶段已走过 35 秒。若还要计算当前阶段剩余时间，需要阶段开始时刻和阶段时长：

\[
t_{\mathrm{remaining}}
=
t_{\mathrm{stage\ end}}-t_{\mathrm{current}}
\]

若状态只提供当前阶段 ID 和周期，算法不能自行假设阶段一定从周期零点开始。不同控制器可能使用周期起点、关键阶段起点或协调相位差作为时间基准。没有基准说明，剩余绿计算会产生系统性偏差。

### 8.1.3 三种状态表达

同一个“当前阶段”，可以用三种方式送到平台，代价完全不同：

具体见表 8-2。
表 8-2 三种状态表达
| 表达 | 内容 | 优点 | 失败条件 |
|---|---|---|---|
| 全量快照 | 每次推送完整状态 | 简单、可缓存、丢一条不影响下一条 | 带宽大、中间状态丢失、时间戳可能重复 |
| 增量事件 | 只推送变化 | 精确、可重放、能还原过程 | 需要顺序、去重和“先取一次快照”的恢复流程 |
| 区间记录 | 阶段开始与结束成对 | 便于评价和回放 | 结束事件丢失会让区间悬空 |

WaySense 的实时状态走的是全量快照加周期刷新：平台每隔一段时间拉取或接收一份完整状态，而不是逐条消费阶段变化。这与设备协议差异有关——不同厂商能提供的增量粒度不同，统一成快照最省事。代价是两次刷新之间的阶段变化不可见，评价时不能假设“看到的状态就是全部状态”。

如果要做精确的阶段级评价，需要额外保存阶段区间（开始、结束、方案版本），而不能只靠快照回推。快照回答“现在是什么”，区间回答“过去发生过什么”，两者不能互相替代。

## 8.2 控制模式

实时对象把设备状态分为固定周期、黄闪、全红、关灯、脱机、定灯、人工、自适应、感应协调和区域协调等模式。

这些模式具有不同的阶段语义。黄闪、全红或脱机时，未必存在正常放行阶段。状态校验不能统一要求 `current_stage_id` 非空。

SignalLab 将模式定义为枚举，并允许特定异常模式没有当前阶段：

```python
state = SignalState(
    site_id="S1",
    observed_at_epoch_s=1000,
    cycle_s=90,
    elapsed_s=0,
    control_mode=ControlMode.OFFLINE,
    current_stage_id=None,
    source="vendor-adapter",
)
state.validate()
```

这避免为了通过数据模型校验而伪造一个阶段。

### 8.2.1 模式决定可用字段

控制模式不是展示文本，它改变状态字段的约束：

具体见表 8-3。
表 8-3 模式决定可用字段
| 模式 | 当前阶段 | 周期 | 是否可确认新方案 |
|---|---:|---:|---:|
| 固定周期 | 应有 | 应有 | 可以，需版本和新鲜度匹配 |
| 自适应 | 应有 | 应有 | 可以，需方案或配置版本 |
| 人工 | 不一定 | 不一定 | 不能，人工操作可能覆盖方案 |
| 黄闪、全红、关灯 | 可以无 | 可以保留 | 不能当作正常配时执行 |
| 脱机 | 可以无 | 可以无 | 不能确认远程方案已生效 |

适配器需要把这些差异显式表达。为了统一数据库字段而给黄闪状态填一个假阶段，会让前端显示一个不存在的绿灯，也会让命令确认逻辑产生误判。

## 8.3 时间状态

对正常周期，需要满足：

```text
0 <= elapsed_s < cycle_s
```

相位差的合法范围通常与周期有关。阶段时间轴还应满足开始时间、结束时间单调，并且周期总时长与阶段列表相符。

时间戳需要区分：

- 设备采集时间
- 平台接收时间
- 数据推送时间
- 方案预期生效时间

用接收时间代替采集时间会让网络延迟被误认为交通状态变化。

### 8.3.1 时间区间与边界

对 `elapsed_s` 通常要求：

\[
0\le e<C
\]

当 \(e=C\) 时，设备应报告下一周期或新的周期起点。若厂商把周期终点也映射为同一个周期，平台可能把边界值写入 `elapsed_s=C`。校验器应拒绝它，或根据设备语义把它规范化为 0 并带上新周期标识，不能同时接受两种含义。

阶段时间还应满足：

\[
0\le t_{\mathrm{stage\ start}}
\le t_{\mathrm{stage\ end}}
\le C
\]

若设备使用绝对时间，时间需要带时区和夏令时规则。多数交通控制内部使用单调时钟或本地控制周期，但平台日志需要可还原的 UTC 时间。把本地墙上时间直接相减，在时钟调整日会产生 3600 秒或重复小时的问题。

### 8.3.2 把循环时间写成区间

只用“当前阶段 ID”不能判断某个时刻是否处于该阶段绿灯。更严谨的表示是半开循环区间：

\[
I=[s,(s+d)\bmod C)_C
\]

其中 \(s\) 是阶段或绿灯起点，\(d\) 是持续时间，\(C\) 是周期。区间跨越周期末尾时，它同时覆盖 `[s, C)` 与 `[0, (s+d)-C)`。若阶段从 116 秒开始并持续 34 秒，则有效区间为：

```text
[116, 150)
```

这个例子恰好结束在周期边界。若持续 40 秒，则覆盖 `[116,150)` 与 `[0,6)`。循环区间的实现需要使用统一模运算，不能让正向扫描和反向扫描各自处理边界。

SignalLab 的 `CircularInterval` 用逐秒计数验证交集，边界案例较小，便于手工检查：

```python
window = CircularInterval(start_s=85, duration_s=10, cycle_s=90)
window.contains(89)   # True
window.contains(0)    # True，因为 90 秒被归一化为 0
window.contains(5)    # False，半开区间不包含终点
```

逐秒计数适合教材和少量验收，不适合直接扩展到大周期全网扫描。生产中可以把两个区间拆成最多四个非环绕区间，用端点比较计算交集。两种实现需要通过相同边界测试。

阶段时间轴使用同一时间定义。设各阶段总时长为 \(T_1,\dots,T_n\)，累计起点为：

\[
s_1=0,\qquad s_{k+1}=s_k+T_k
\]

校验器需要证明：

\[
s_{n+1}=C
\]

并且每个时刻恰好属于一个阶段。若只检查每个阶段时长非负，仍可能留下重叠或空洞。

### 8.3.3 从绝对观测时间恢复周期内位置

设备提供绝对观测时间 \(t_{\mathrm{obs}}\) 和某个已知周期起点 \(t_0\) 时，周期内秒数可以写为：

\[
e=(t_{\mathrm{obs}}-t_0)\bmod C
\]

秒和周期需要转换为同一整数单位。若两个时间使用不同设备的时钟，\(e\) 会被时钟偏差污染。系统应先校准设备偏移，或直接采用设备上报的周期已走时间，并保留原始绝对时间用于审计。

当 `elapsed_s` 与阶段窗口矛盾时，不能静默修正其中一个字段。例如平台认为 B 阶段从 67 秒开始，设备在 80 秒处上报 C 阶段。差异可能来自方案版本不一致、周期基准不同或适配器映射错误。系统应输出“状态-方案不一致”，并禁止用这个状态自动确认新方案。

## 8.4 状态是否过期

实时状态具有有效期。一个 10 分钟前的正常状态，不能证明设备现在正常。

SignalLab 提供：

```python
state.is_stale(now_epoch_s, max_age_s=30)
```

过期后系统可以保留最后状态用于展示，但不应据此自动确认新方案生效。

### 8.4.1 新鲜度和一致性的联合判断

设状态年龄为 \(a=t_{\mathrm{now}}-t_{\mathrm{event}}\)，新鲜度阈值为 \(A\)。只在 \(a\le A\) 时允许状态参与自动确认：

\[
P_{\mathrm{fresh}}=(a\ge0)\land(a\le A)
\]

若事件时间来自未来，也应拒绝或隔离。它可能是设备时钟错误，也可能是平台和设备的时区配置错误。负年龄不能被当成“非常新鲜”。

新鲜状态也不能单独证明方案生效。确认还要满足：

\[
P_{\mathrm{applied}}
=
P_{\mathrm{fresh}}
\land(\mathrm{plan\ version}=\mathrm{target})
\land(\mathrm{control\ mode\ supports\ confirmation})
\]

在 17:00:00 目标生效时：

```text
16:59:58 observed v41 -> 未到目标时间，等待
17:00:05 observed v41 -> 可能仍在切换，继续等待
17:00:37 observed v42 -> 新鲜且版本匹配，可以确认
17:06:00 observed v42 -> 可能过期，不能证明当前仍在执行
```

超时阈值应由设备切换时间、状态推送频率和业务容忍度共同决定，而不是统一写成 5 秒。

## 8.5 厂商适配

不同信号机提供的状态粒度不同：

- 有的直接给出当前阶段的开始和结束时间
- 有的按相位推送，需要从方案中还原阶段
- 有的只给控制模式和周期
- 厂商模式编号与平台模式编号也不一致

WaySense 通过不同厂商处理服务，将原始数据转换为统一的 `RealTimePhaseStageVO`。这说明接口层的核心工作是语义归一化，而不是把厂商 JSON 原样转发。

适配器至少负责：

1. 厂商控制模式映射到平台模式。
2. 厂商相位或灯组映射到平台阶段。
3. 时间字段统一时区和单位。
4. 缺失字段标记为未知。
5. 保留原始来源和版本，便于排障。

### 适配器的错误策略

如表 8-4 所示。
表 8-4 适配器的错误策略
| 原始问题 | 错误处理 |
|---|---|
| 未知控制模式 | 标记 `unknown`，禁止自动下发 |
| 缺失阶段开始时间 | 保留周期状态，但无法计算剩余绿 |
| 阶段编号不存在于方案 | 状态与方案不一致告警 |
| 旧事件晚到 | 拒绝覆盖更新状态 |
| 数据格式错误 | 保存原始消息摘要并隔离 |

适配器不应在未知模式下自行猜测“正常固定周期”。猜测会把设备异常转换成平台成功。

### 8.5.1 一个厂商映射案例

假设厂商上报：

```text
modeCode = 3
phaseBits = 00110000
cycleStartMs = 1000000
serverReceiveMs = 1000320
```

平台配置认为 `modeCode=3` 是固定周期，但另一版本设备把 3 定义为全红。若适配器只按当前配置翻译模式，历史消息会被错误解释。应记录设备型号、固件版本和协议版本，并把映射表版本写入状态。

`phaseBits` 需要先映射为厂商相位，再通过本路口方案映射为平台阶段。位图无法自动告诉系统某个位代表“东直”还是“东左”，所以适配器需要读取该路口的通道配置。若配置版本与方案版本不匹配，状态只能标记为不可确认。

接收时间比设备时间晚 320 毫秒，这个延迟本身可能正常；但若平台状态在 10 分钟后才处理，自动控制仍不能把它当作实时输入。设备时间用于事件顺序，接收和处理时间用于链路监控。

### 8.5.2 控制模式有三套编码

`ControlModeEnum.java` 里，同一个模式带三个编号：平台内部值、厂商A值、厂商B值。为避免指向具体厂商，本节用厂商A、厂商B代指两家设备厂商；厂商C在平台章节出现。节选：

具体见表 8-5。
表 8-5 控制模式有三套编码
| 模式 | 内部 | 厂商A | 厂商B |
|---|---:|---:|---|
| 定周期 | 1 | 23 | "21" |
| 全红 | 3 | 26 | "12" |
| 自适应 | 8 | 0 | "23" |
| 无缆协调 | 11 | 21 | "-1" |
| 区域协调 | 14 | 0 | "-1" |

两点后果：

1. 8/9/10/12/13/14（自适应、半感应、全感应、感应、动态、区域协调）在厂商A侧一律映射为 `0`，厂商B侧多为 `"-1"`，等于“该厂商无法表达这个模式”。如果平台把 `0` 当定周期、把 `-1` 当未知，控制模式会被静默改写。
2. 映射应当是一张“厂商 × 模式”的二维表，并记录映射表版本。用一个枚举值直接跨厂商传递，迟早错位。

另外，“全红”既是控制模式（值 3），又是过渡灯色里的红灯（值 2、时长 2 秒），同名不同义。配置和日志里需要靠字段名区分，不能只靠值。

## 8.6 状态事件与消息链路

实时控制模式、周期、阶段和交通流分别通过不同事件进入平台。生产系统使用 Kafka 向数据平台和前端推送事件。

事件消费需要处理：

- 重复消息
- 乱序消息
- 延迟到达的旧状态
- 同一路口多次状态更新
- 设备重连后的状态跳变

一个简单规则是使用事件时间和版本号比较。对于同一路口和设备，较旧的事件不能覆盖较新的状态。只按消息到达顺序更新，会把网络重传当成真实状态回退。

### 8.6.1 分区键与重复消费

Kafka 中同一路口的状态更新通常应使用稳定的 `site_id` 或设备键作为分区键，使同一设备事件进入同一分区并按发送顺序消费。跨分区无法保证全局顺序，不能用一个消费者线程的到达顺序推断路口时间。

即使同一分区，生产者在重试时也可能重复发送。消费者应以事件唯一键幂等写入，例如：

```text
event_key = site_id + device_id + event_time + vendor_sequence
```

重复消息的写入结果应与第一次相同，不重复增加阶段统计，不重复触发告警。若消息带的是完全相同的事件键但内容不同，应视为冲突，而不是最后到达者覆盖。

流处理还应区分事件时间和处理时间窗口。统计“10:00 至 10:05 的阶段次数”应按事件时间，监控消费者积压应按处理时间。Kafka/Flink 中的水位线和窗口关闭策略要与信号窗口的半开区间一致。

### 8.6.2 状态重连后的跳变

设备断线 45 分钟，重连后直接上报当前周期。平台看到的状态从 17:00 的 `stage A` 跳到 17:45 的 `stage C`，中间没有连续事件。系统应记录“观测断档”，不能用当前状态推算每一秒的历史阶段。

如果运行状态缓存需要连续性，可以生成带 `source=gap-filled` 的估算记录，并降低置信度；原始状态表仍要保留空档。对控制评价而言，空档意味着不能完整计算周期级指标，不能把缺失区间默认为所有方向都畅通。

## 8.7 状态与命令

方案命令和运行状态构成两个状态机。

```text
Command: requested -> accepted -> observed
Operation: fixed -> adaptive -> manual -> offline
```

命令状态是“我们要求什么”，运行状态是“设备现在是什么”。只有两者在同一批次、同一方案版本和同一时间窗口下匹配，才能确认方案生效。

设备回复成功却观察到旧方案，应标记为执行不一致，而不是直接成功。

### 一致性确认键

匹配命令和运行状态时，至少比较：

```text
siteId
planVersion
batchId / sequenceId
observedAt
controlMode
```

设备未回传批次 ID 时，仍需使用方案编号、阶段和预期生效窗口进行弱确认，并明确确认强度。

### 8.7.1 命令与观测的联合状态

命令状态机和运行状态机应分别保存，再计算联合视图：

具体见表 8-6。
表 8-6 命令与观测的联合状态
| 命令状态 | 运行观测 | 联合判断 | 下一步 |
|---|---|---|---|
| accepted | 旧方案、未到目标时间 | 等待生效 | 继续观察 |
| accepted | 旧方案、已超时 | 执行未确认 | 告警、重试或回滚 |
| observed | 新方案 | 执行成功 | 进入效果评价 |
| observed | 人工模式 | 运行覆盖 | 不得标为自动控制成功 |
| failed | 旧方案 | 未执行 | 保持原方案并记录 |
| failed | 新方案 | 状态矛盾 | 高优先级核查 |

只有联合视图能回答“我们的控制意图是否成为实际运行状态”。单独统计 `accepted=95%` 会把设备协议成功误报成控制成功；单独统计运行状态“在线率 98%”也不能说明方案执行正确。

## 8.9 小结

第 7 章把“方案应该是什么”算清楚了，这一章回答“设备此刻在执行什么”。四个时间坐标定位一次观测，控制模式界定字段约束，循环区间和时间校验划出合法边界，过期判断给状态标上保质期。厂商适配把各方言译成统一语义，消息链路守住顺序与幂等，一致性确认键最终把命令和观测对到同一批次。状态可信，自动化才有地基；状态过期、矛盾或缺失时主动降低自动化权限，是这套机制的最后防线。

至此，第二部分完成了从检测到控制输入的整条链路——流量、质量、参数与状态都已就位。第三部分进入单点信号控制：先拆开路口的时间骨架，讨论相位、阶段、环与相序。

## 第二部分评点：先把坏数据当坏数据

数据最会骗人的地方，不是它缺了，而是它看起来没缺。

一个检测器离线，平台补了一个值；一个视频跟踪丢了目标，置信度仍然是 1；一个 15 分钟窗口里只有 3 分钟有效，报表照样给出平均值。这些数据进入算法时，格式没有问题，字段也没有缺失，唯一缺的是“它能不能被信”。

第二部分把这件事拆成四层：检测、质量、容量、状态。检测回答“有没有看见”，质量回答“看见的能不能用”，容量回答“这些流量意味着多大的供给”，状态回答“设备此刻到底在执行什么”。四层里任何一层含糊，后面的配时和评价都会建立在一个看起来正常的数字上。

这一部分最容易被读成数据处理技巧，其实它讲的是证据等级：实测、补全、估计、猜测，不能混在一个 `flow` 字段里。现场最危险的不是没有数据，而是坏数据穿着好数据的外衣。

所以这一部分讲的不只是数据清洗。它是在给每一个进入算法的数字标上来源和可信度；数字从哪来，比数字本身更值得先问。
