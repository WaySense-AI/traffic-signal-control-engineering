# 第 3 章 用数据描述一个路口

交通工程师看路口时，看到的是进口道、车道功能、冲突点和允许的转向；软件系统看到的是节点、几何、对象 ID 和关联关系；算法看到的可能只是一张“方向—流向—流量”表。三种视角描述的是同一个路口，用的却是三套词汇。只要这三套表示各自为政，每接入一个新服务，就要重新解释一遍相同的概念，而每次解释都可能产生新的偏差。

设想一个具体的星期：周一，地图组把 S2 东进口的渠化录入为“两直一左”；周三，信号组的方案里它还是“两直一左”；周五，算法组的流量表里只剩 `east-straight` 和 `east-left` 两行——没人做错什么，三个组各自忠实于自己的数据来源。某个夜间，路口渠化因施工改为“两直一共享左”，三个组里只有一个更新了记录。从那天起，同一个路口在系统里就有了三个版本的自己，此后每一次数据对不上，追查的起点都回到那张拓扑表。统一的数据模型要解决的，正是这类“各对各的账”的问题。

本章从道路几何开始，逐层建立到信号方案的数据模型，目标用一句话说清：一个路口需要被表示到什么程度，才能同时支撑渠化展示、信号参数编辑、配时优化、方案下发和效果评价这五类工作。模型沿这条链展开——路网与路口的身份、车道与流向的映射、相位与阶段、绿信比与相位差，最后到方案库与调度。

## 3.1 从道路网络到信号路口

交通控制需要知道“车辆从哪里来、经过哪个路口、到哪里去”。完整路网通常由节点和路段构成：

```text
Node <--- Road ---> Node
```

`Node` 是空间连接点，`Road` 或 `Link` 是两个节点之间的道路区段。信号路口不是普通节点的简单同义词，它需要绑定信号控制设施、车道、相位和方案。

WaySense 的现有模型中，`Node` 保存路网位置和节点类型，`Road` 保存上下游节点、几何、长度和道路等级，`Site` 表示受控制的路口。一个节点可能没有信号控制，一个路口还可能存在主路口和附属路口关系。

由此得到本章第一个建模原则：

> 空间位置、交通对象和控制对象需要分开命名。

如果把所有交叉口都直接叫 `Site`，路网分析会把几何节点和受控设备混在一起；如果只看 `Node`，又会丢失信号方案和厂商信息。

### 3.1.1 一个路口对象的稳定身份

在四路口走廊中，S2 可以同时拥有：

```text
site_id       = site-S2
node_id       = node-S2
vendor_id     = controller-17
display_name  = 中山路-建设路
```

这四种标识服务于不同系统。`site_id` 是平台控制对象，`node_id` 是路网拓扑节点，`vendor_id` 是信号机设备，`display_name` 是人读名称。把某个字段当作全局主键，可能在设备更换、中文名修改或路网重导后破坏历史关联。

对象还需要有效期。S2 在道路施工期间可能更换信号机，旧设备的状态不能继续写入新设备的运行记录。可以给设备引用增加：

```text
valid_from
valid_to
source_system
source_version
```

拓扑导入也需要版本。若车道渠化在 10 月从“两直一左”改为“两直一共享左”，旧流量记录仍应能追溯到当时的车道映射，不能用新映射重新解释全部历史数据。

## 3.2 道路、进口道和车道

道路区段描述两个节点之间的连续空间，但信号控制更关心某个路口进口道的车道功能。

一个进口道可能包含：

- 一条或多条左转车道
- 一条或多条直行车道
- 右转车道或右转与直行共用车道
- 公交专用、非机动车或行人通道

同一物理道路在不同方向、不同路口可能具有不同渠化。因此不能只用一个 `Road` 对象表达所有进口车道。

生产模型还使用 `Roadway`、`IoSection`、`VLane`、`Channel` 等对象区分道路、道路方向、进口或出口断面、虚拟车道和控制通道。这里的关键是三个问题：

1. 这条车道属于哪个进口方向？
2. 它允许哪些转向？
3. 它由哪个信号控制通道或相位控制？

第一个问题用于流量映射，第二个用于冲突和相位设计，第三个用于设备命令。缺少任一关系，系统都可能在展示上正确、在控制上错误。

### 3.2.1 车道到流向的映射公式

设车道 \(l\) 的观测流量为 \(q_l\)，它允许的流向集合为 \(\mathcal{M}(l)\)，流向 \(m\) 在该车道中的分配比例为 \(a_{l,m}\)。方向或转向流量可由下式聚合：

\[
q_m=\sum_{l:\,m\in\mathcal{M}(l)} a_{l,m}q_l
\]

且对每个车道：

\[
\sum_{m\in\mathcal{M}(l)}a_{l,m}=1,\qquad a_{l,m}\ge 0
\]

例如 S2 东进口有三个车道：

具体见表 3-1。
表 3-1 车道到流向的映射公式
| 车道 | 允许流向 | 流量 veh/h | 分配 |
|---|---|---:|---|
| E1 | 直行 | 600 | 直行 100% |
| E2 | 直行 | 500 | 直行 100% |
| E3 | 直行/左转 | 400 | 各 50% |

则东直为 `600 + 500 + 200 = 1300` veh/h，东左为 `200` veh/h。这个结果只是流量映射结果，不代表一条共享车道在排队时会始终按 50/50 运行。交通组成、信号阶段和排队优先级会改变共享车道的实际转弯比例，所以映射比例应标注来源和适用时间窗。

若 E2 数据缺失，不能只把 E2 当作 0 然后得到东直 800 veh/h。缺失值应该向上传播：

```text
east-straight.volume = None
east-straight.missing = 1
east-straight.confidence = 0.0
```

下游可以尝试短时补全、上游下游守恒或人工值，但需要保留 `estimated`、`confidence` 和数据来源。`None` 与 0 的区别，是数据传递中最重要的一条规则。

现实中的共享车道比例还会使用车道数、方向和饱和流率修正。WaySense 的 `DigitalIntersection` 和流向映射工具会根据车道参数与拓扑系数分配流量；教学代码只保留最明确的等分规则，用来验证映射的基本不变量；等分不能代表所有路口。

## 3.3 相位：一组同时放行的交通流

相位图常被画成若干箭头同时亮起，但相位的数据含义是“一组可以同时获得通行权的交通流”。几何箭头只是可视化结果。

WaySense 的 `Phase` 对象包含：

- 相位编号
- 控制的通道位图
- 可并发相位位图
- 最小绿
- 最大绿
- 单位延长绿
- 失去和获得路权时的过渡灯色及时间
- 是否为虚相位

位图是一种紧凑存储方式。例如 `controlChannel` 用整数的若干位表示通道是否受该相位控制，`currencyPhase` 用若干位表示哪些相位可以同时放行。

位图适合设备配置，却不适合直接解释。代码读取位图后，应先转换为通道 ID 集合或相位 ID 集合，再做冲突和合法性检查。

```text
存储表示：Long 位图
业务表示：{channel-1, channel-2, channel-5}
系统含义：这组通道可以同时获得通行权
```

第二个建模原则是：

> 紧凑编码应与业务语义分离。

数据库可以继续使用位图，但算法的输入应是可读、可验证的流向和相位集合。

读取位图时，可以使用最低位到最高位的循环完成可读转换：

```python
def decode_channels(mask: int, channel_count: int) -> tuple[str, ...]:
    return tuple(
        f"channel-{index + 1}"
        for index in range(channel_count)
        if mask & (1 << index)
    )
```

生产代码不能只凭解码结果判断安全。位图可能包含未配置的通道、设备型号不支持的位或人为填错的位。解码后还需要对照 `Channel` 配置检查每个通道是否存在、属于哪个进口、控制哪些流向，再进入冲突图。

## 3.4 从相位到阶段

相位表示可同时通行的交通流，阶段表示周期中一个持续放行区间。一个阶段可以包含一个或多个相位。

```text
Phase A = {east-left, east-through}
Phase B = {west-left, west-through}
Stage AB = {Phase A, Phase B}
```

如果东西向的直行和左转互不冲突，可以把它们放入同一阶段；如果存在冲突，就需要拆成不同阶段或通过保护规则解决。

生产模型中的 `PhaseStage` 保存阶段编号、所控制相位列表、是否为搭接阶段和阶段图片。`SplitSequence` 则保存阶段在一个信号序列中的顺序和虚拟时长。

这两个对象回答不同问题：

- `PhaseStage`：这个阶段放行什么？
- `SplitSequence`：这个阶段在周期中的哪里？

只保存阶段内容，不保存顺序，无法确定清空关系和协调阶段。只保存顺序，不保存相位集合，无法验证冲突。

## 3.5 环和阶段序列

简单路口可以使用单一固定阶段序列：A、B、C、D 循环执行。更复杂的交叉口支持多环、搭接和相位灵活切换。

`Ring` 的作用不是增加一个数据库表，而是表达哪些阶段可以组合、哪些顺序需要保持、哪些相位可以跨阶段搭接。生产实现使用 `RSplitPlan`、`SplitSequence` 和相位并发关系组织这些信息。

算法层通常不需要保存完整环图。它会先把当前方案转换为：

- 阶段集合
- 阶段到关键流向的映射
- 阶段序列
- 阶段最小绿与清空时间

然后进行周期和绿信比计算。

这里有一条安全规则：

> 只优化时间时，阶段顺序保持不变；只有明确执行相序重设计时，才允许生成新序列。

否则，一个原本兼容的绿信比方案可能被算法替换成不同阶段顺序，破坏相位的清空关系和路口标线含义。

阶段集合与顺序应分别验证。设当前方案阶段序列为 \(S=(s_1,\ldots,s_n)\)，候选方案序列为 \(S'\)。只调时间时要求：

\[
S'=S
\]

集合相等不能替代序列相等。若当前方案为 `A-B-C-D`，候选方案为 `A-C-B-D`，两边的阶段集合完全相同，但 `B` 与 `C` 之间的清空关系、关键阶段位置和协调相位可能都发生变化。生产代码用相序兼容筛选候选方案，原因就在这里。

## 3.6 绿信比方案

`SplitPlan` 表达一个信号周期和阶段时间分配。生产模型支持两类数值：

- 百分比
- 绝对秒数

`SplitPlanDetail` 保存每个阶段的数值、顺序关系和特殊约束，例如是否主阶段、是否可跳过、是否可以获得相邻阶段时间。

百分比与秒数不是单纯的显示格式差异。使用百分比时，修改周期会改变实际阶段时长；使用秒数时，周期需要与阶段总时长保持一致。代码在转换两类表示时需要重新校验：

```text
阶段时长之和 = 周期
每个阶段时长 >= 最小安全时间
阶段顺序与方案版本一致
```

`ControlPlan` 进一步把绿信比方案和相位差方案组合成一个控制方案。它不重新定义阶段，只引用相关方案。

```text
ControlPlan
  +-- SplitPlan
  |     +-- Cycle
  |     +-- Stage durations
  +-- OffsetPlan
        +-- key site
        +-- critical stage
        +-- offset
```

这种引用关系避免在多处复制周期和阶段时间，但也要求版本一致性。方案被编辑后，旧的组合方案需要明确失效、更新或保留为历史版本。

### 3.6.1 百分比与秒数的转换

设周期为 \(C\)，阶段 \(i\) 的百分比为 \(p_i\)，阶段总时长为：

\[
T_i=C\frac{p_i}{100}
\]

如果设备只接受整数秒，直接四舍五入可能得到：

\[
\sum_i \operatorname{round}(T_i)\ne C
\]

例如周期 90 秒、三个阶段比例分别为 33.3%、33.3%、33.4%，完整乘积为 29.97、29.97、30.06 秒。它可以表达总周期，但不能直接作为整数灯时。若先分别四舍五入，某些比例的边界值会多出或少掉 1 秒。更可靠的做法是先分配整数总时长，再把余数按确定顺序补齐。附录 B 给出通用公式。

这里需要记住语义：百分比适合表达编辑器和人工配置意图，秒数适合设备执行和周期校验。两者之间的转换应当是一次完整的整数化过程，而不是逐阶段随手 `round()`。

## 3.7 相位差方案

绝对相位差方案通常保存：

- 基准路口
- 关键阶段
- 协调位置
- 主相位差
- 高低周期下的相位差

相对相位差还可以保存相邻路口和连接阶段。相位差不是独立于绿信比方案存在的绝对属性，它依赖周期、关键阶段和阶段序列。

因此，校验相位差时至少需要确认：

1. 基准路口存在。
2. 关键阶段存在于两个相关方案。
3. 周期关系满足协调要求。
4. 相位差位于合法范围。
5. 同一子区中的计算使用同一时间基准。

## 3.8 从方案库到调度

一个方案库保存“可以用的方案”，调度保存“什么时候用哪个方案”。

生产模型通过 `ControlPlan`、`DayPlanInfo`、`DayPlanContent` 和 `SchedulePlanInfo` 等对象组织这层关系。概念上可以简化为：

```text
Plan library
  -> Day plan: time of day -> selected control plan
  -> Schedule: month/weekday/date -> selected day plan
```

算法推荐通常生成一个候选控制方案，再由人工或规则决定是否进入方案库、日计划和调度。不能把“算法返回一个方案”直接等同于“调度已经配置”。

### 3.8.1 方案版本是组合出来的

书里多次说“版本一致”，但现有实现没有 `plan_version` 字段。所谓“策略版本”是组合出来的：策略库表 + `scope` + `month` 位图 + `status`（1 废弃 / 2 正常），查询条件形如 `WHERE month=%s AND scope=%s AND status=2`（`crossDataDb.py`）。

后果有三条：

- 版本比较不能只比一个数字；同一方案号在不同 `scope`、不同月份位图下可能是不同版本。
- 历史版本没有独立版本号，审计只能靠记录表和状态变更日志。
- 新接口若只传 `planId`，接收方无法判断这是哪个版本。

位图本身也有约定：月份、星期、日期、相位集合、通道集合都用整数位图存储，编号从 1 开始，对应 `bit(编号-1)`。工具方法名字叫 `listToOctal`，实现却是 `1L << (i - 1)`（`BinaryUtil.java`），名字和语义不符，读代码时不要被名字误导。

## 3.9 子区与空间关系

单路口模型解决本地放行，子区模型增加路口之间的空间关系。子区至少需要：

- 参与路口
- 连接路段
- 路段长度
- 正反方向协调速度
- 关键路口
- 协调方向

`Link` 的上下游关系决定哪些路口需要一起协调，路段长度和速度决定理论行程时间。只有路口列表而没有有向连接，无法计算有效相位差。

## 3.10 一个可运行的最小表示

SignalLab 目前只实现最核心的时间模型：

```python
SignalStage(
    stage_id="A",
    green=30,
    green_flash=3,
    yellow=3,
    all_red=2,
    min_green=12,
    phase_ids=("east-through", "east-left"),
)
```

阶段总时长由四个时间分量计算：

```text
duration = green + green_flash + yellow + all_red
```

方案需要满足：

```text
sum(stage.duration for stage in plan.stages) == plan.cycle
```

教学模型没有把绿闪、黄灯和全红合并成一个 `clearance` 字段。各分量分别保留后，系统才能检查设备配置、统计纯绿和展示实际灯色。

从数据模型到执行的调用链可以这样阅读：

```text
LaneObservation
  -> aggregate_lane_movements
  -> MovementDemand
  -> stage_flow_ratios
  -> cycle / split allocation
  -> SignalPlan
  -> validate_plan
```

`LaneObservation` 负责保存车道流量、是否估计和置信度；映射函数把车道记录变成方向/流向记录；需求对象绑定饱和流率；周期算法只读取需求，不再回头猜测原始检测器的状态。分层的关键是每一层都保留必要来源，并且不让下层字段悄悄改变含义。

运行一个映射实验：

```python
from signal_lab import LaneObservation, aggregate_lane_movements

flow = aggregate_lane_movements([
    LaneObservation("E1", "east", "straight", 600),
    LaneObservation("E2", "east", "straight", 500),
    LaneObservation("E3", "east", "straight_left", 400),
])

print(flow[("east", "straight")])
print(flow[("east", "left")])
```

预期东直为 1300 veh/h，东左为 200 veh/h。把 E2 的流量改为 `None`，东直结果应变为缺失而不是 1000 或 1300。再复制一个 E2，程序应拒绝重复车道，而不是把两次记录相加。三个观察分别验证数值映射、缺失传播和实体唯一性。

## 3.11 本章实验

1. 为一个南北直行、东西直行、东西左转的四阶段路口建立阶段对象。
2. 判断哪些阶段可以共享相位，哪些阶段需要保持顺序。
3. 把一次 120 秒周期的百分比绿信比转换为秒数，再转换回百分比，记录舍入误差。
4. 为一个包含四个阶段和三个连接路段的子区写出最小数据对象。
5. 给 S2 的 E3 共享车道增加 `assignment_source` 字段，说明按固定比例、历史转向比例和饱和流率修正三种方法的适用条件。
6. 把周期 100 秒、阶段比例 `21.5%`、`28.5%`、`19%`、`31%` 转换成整数秒，要求总和仍为 100 秒。记录每个阶段的舍入误差。
7. 模拟道路施工改变一条车道功能，说明为什么旧观测、新拓扑和方案版本需要分别引用各自的有效期。

## 3.12 小结

回头看本章建立的这些对象，会发现它们各自守护着一种不同的时间。`Node`、`Road`、`Site` 描述路口此刻的空间；车道映射带着拓扑版本，记录的是导入那一刻的空间；相位和阶段表描述此刻的通行权；方案库保存曾经生效过的历史版本；调度是其中唯一看向未来的部分，它决定明天早上哪个版本上线。五种时间各自由 ID 和有效期确定，“S2 下午三点跑的到底是哪个方案”这类问题才答得清楚——答不清这个问题，后面的优化、下发、评价都会失去可靠基础。

相位回答“谁可以同时走”，阶段回答“这一时间段放行谁”，阶段序列回答“什么时候走”，绿信比方案回答“各阶段走多久”，相位差方案回答“相邻路口如何错开”。至此，一个路口的静态模型已经完整：身份稳定、映射可追溯、版本可对账。这份“正确”还要再检查一遍——哪些冲突关系需要被结构约束挡住、哪些数值边界一步都退让不得、设备失联之后如何降级——这些是第 4 章“信号控制系统的正确性不变量”的主题。第二部分则从交通检测开始，让这套模型接入实时流量。
