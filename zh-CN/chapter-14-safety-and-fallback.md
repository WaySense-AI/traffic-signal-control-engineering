# 第 14 章 配时安全与故障降级

第 13 章末尾留下一个问题：设备离线、数据过期、方案未校验、控制模式被人工切换时，自动化在哪里停下来、谁来接管。本章正面回答它。交通信号系统的自动化权限依赖完整状态——算法返回结果只说明“算出了什么”，说明“此刻是否可执行”需要另取证据；四个故障源中有一个脱落，一个数学上正确的方案就可能变得不可执行。

17:19:40，平台最后一次收到 S4 的心跳；17:20:00，S4 的 4G 链路静默中断，设备仍在按最后下发的方案运行。17:20:03，算法完成新候选，下发队列里排着 S1 到 S4 四条命令。此刻若只看“算法返回了结果”就放行，S4 会在离线状态下收到一条生效状态无从确认的命令——控制意图与实际状态就此分家。本章把这类判断组织成“允许自动化”的门控条件，并讨论失败时的降级路径。

一个安全门控需要有确定的优先级。假设设备离线、输入置信度低、方案也未通过校验，三个条件都在拒绝，系统最终只能进入一个状态。如果只看代码中最后一个 `if`，结果可能随字段顺序变化；如果只返回一组原因，运营人员又不知道应该先处理什么。

本书采用保守原则：运行时稳定优先于算法优化，执行确认优先于控制意图，已知合法方案优先于未经审核的候选；门控条件按风险和恢复能力排序，权重取决于故障发生后的恢复难度。

## 14.1 自动控制前置条件

执行自动方案前，至少需要确认：

- 方案已经通过完整校验
- 实时数据足够新
- 信号机在线
- 当前控制模式允许自动控制
- 输入置信度达到阈值
- 目标设备支持方案参数

SignalLab 使用：

```python
readiness = AutomationReadiness(
    plan_validated=True,
    telemetry_fresh=True,
    device_online=False,
    control_mode_allows_automation=True,
    input_confidence=0.9,
)

readiness.can_auto_apply  # False
readiness.rejection_reasons()
# ("device is offline",)
```

每个拒绝原因都应可被日志和界面解释。

### 14.1.1 门控条件全部为真才放行

把条件写成相加的评分会有明显问题。设备离线一次和设备不支持某个阶段都可能导致成功率为零，不能因为输入置信度高就“抵消”一部分。更合理的表达式是：

\[
\begin{aligned}
P_{\mathrm{auto}}
=P_{\mathrm{valid}}\land P_{\mathrm{fresh}}\land P_{\mathrm{online}}\\
\quad \land P_{\mathrm{mode}}\land P_{\mathrm{confidence}}\land P_{\mathrm{device\ support}}
\end{aligned}
\]

各项都应为真。若需要表达有限的“警告但仍可继续”，应单独定义可继续的条件和持续时间，而不是把硬失败变成一个小扣分。

### 14.1.2 前置检查的输入快照

门控需要在同一决策快照上判断。假设 17:00:00 读取到阈值 0.7、置信度 0.8、设备在线 true；17:00:01 设备离线；17:00:02 算法完成。如果最终仍使用旧快照自动下发，设备在线状态已经失效。

门控快照至少记录：

```text
snapshot_time
data_window_end
telemetry_observed_at
device_last_seen_at
current_plan_version
observed_plan_version
control_mode
input_confidence
config_version
```

每个字段有自己的观测时间和有效期。系统不能把数据置信度的 `snapshot_time` 当作设备心跳时间，也不能把方案版本当成运行状态版本。

## 14.2 降级等级

故障不只有“正常”和“停止”两种状态。可以采用分级降级：

降级等级如表 14-1 所示。

<!-- pagebreak -->
表 14-1 降级等级
| 状态 | 系统行为 |
|---|---|
| 正常 | 可计算、可推荐、可自动下发 |
| 受限 | 保持自动运行，但禁止新方案 |
| 推荐降级 | 只展示建议，等待人工确认 |
| 固定方案 | 回到已审核的固定方案 |
| 本地控制 | 设备或现场控制系统接管 |
| 离线 | 停止依赖平台的新决策 |

降级等级应取决于故障类型。短时数据质量下降不一定需要立即切人工，通信中断则不能继续依赖云端实时命令。

### 降级判定伪代码

```text
if device is offline or telemetry is stale:
    keep last safe plan
    disable new automatic commands
elif plan is not validated:
    reject candidate
elif input confidence is low on a critical movement:
    generate recommendation only
elif all safeguards pass:
    allow automatic apply
```

顺序很重要。设备离线时继续运行算法预测没有直接危害，但继续下发新命令会让意图和实际状态分离。

### 14.2.1 状态优先级

实现降级时推荐按以下优先级判断：

1. 是否存在已知安全模式，例如全红、黄闪或设备本地控制。
2. 设备是否在线、心跳是否新鲜、控制模式是否允许自动命令。
3. 当前方案是否已发布且完整。
4. 输入数据是否足够新，关键阶段是否满足置信度门槛。
5. 候选方案是否已校验且设备支持。
6. 是否满足协调、公共周期和版本兼容。
7. 只有全部通过，才允许自动下发。

前面的条件失败时，后面的优化结果仍然可以计算和展示，但不能提高执行权限。例如设备离线时，算法可以继续生成候选用于恢复后的审核，但命令状态应当是 `blocked_by_device`。

设备恢复顺序也要明确：

```text
offline
  -> connected
  -> state synchronized
  -> plan validated against observed state
  -> monitoring
  -> automatic control enabled
```

“connected” 只表示网络可达，不表示运行状态可信；“state synchronized” 才允许确认版本和控制模式；“plan validated” 才允许下发。

### 14.2.2 每个路口都有自己的降级状态

同一平台里，不同路口可能处于不同状态。S1、S2 正常，S3 输入低置信度，S4 设备离线。一个子区自适应请求不能把整体标签写成简单的 `degraded` 就继续以统一方式下发。

可以按路口记录：

```text
S1: automatic
S2: automatic
S3: recommendation_only
S4: hold_last_safe_plan
```

如果协调算法要求所有路口使用同一公共周期和方案批次，S3、S4 的降级可能使整个子区不能执行新方案。此时系统需要选择保持全局原方案、拆分协调关系或等待恢复。安全状态不能只靠各路口字段拼接，需要回到协调约束重新判断。

### 14.2.3 三种门控实现

同一个“是否允许自动下发”，可以写成三种结构：

具体见表 14-2。
表 14-2 三种门控实现
| 实现 | 结构 | 优点 | 失效条件 |
|---|---|---|---|
| 串联 if | 按优先级逐个判断，失败即返回 | 顺序显式、失败快 | 顺序写错；多个 `if` 只看最后一个；拒绝原因不完整 |
| 加权评分 | 各条件打分求和，过线放行 | 能表达“轻微不足” | 高分项抵消硬故障；设备离线也可能过线 |
| 显式状态机 | 状态 + 事件 + 守卫条件 | 可审计、可测试、可回放 | 实现成本高，状态设计错会形成永久等待 |

本系统是第一种：14.2.1 的七级优先级就是串联判断。它的风险不在逻辑本身，而在实现细节——顺序被后续修改打乱、某个分支忘记 `return`、拒绝时只返回“不可用”而不给原因。

加权评分看起来更“科学”，但对安全门控是错的：设备离线是硬约束，不能因为数据置信度高就被抵消。这一点 14.2 已经用“相加评分”的反例说明过。

状态机适合条件多、需要回放的场景。无论选哪种，验收要求相同：**每次拒绝都要能说出是哪一条、当时的快照是什么、谁改过规则**。

## 14.3 设备离线

设备离线时：

- 最后状态可以展示，但需要标记过期
- 新方案不能确认为已生效
- 不应根据离线前状态持续自动调整
- 恢复后先同步实际状态，再允许新命令

设备重连时的状态可能已经与平台预期不同，不能直接把恢复事件当作新方案成功。

### 14.3.1 离线时间与本地时钟

设备在线时，平台可以依赖自己的时钟协调命令；设备离线后，本地控制器继续按自己的时钟运行。恢复时，平台应获取设备周期起点、当前阶段和运行方案，而不是根据离线前状态推算。

设离线时最后观察到周期起点为 \(t_0\)，离线持续 \(L\) 秒，若设备周期固定为 \(C\)，理想周期相位为：

\[
\phi=(t_{\mathrm{now}}-t_0)\bmod C
\]

这个公式只能给展示层一个估计。设备可能在离线期间切换了方案、进入黄闪、被人工调整或发生时钟漂移。没有直接状态时，不能把它作为自动确认或安全联锁的证据。

设备恢复后还应检查配置版本。离线期间道路施工可能改变阶段和通道，旧方案即使数值仍合法，也可能不符合新渠化。

## 14.4 数据过期与低置信度

低置信度输入可以用于生成推荐，但应限制自动执行。策略可以按关键阶段区分：

```text
非关键方向低置信度：允许保持原方案
关键阶段低置信度：进入推荐或固定方案
关键拓扑缺失：停止自动计算
```

“保持原方案”本身也需要检查原方案是否存在、是否仍被支持。

### 14.4.1 输入质量的时效衰减

一个 15 分钟流量窗口在 17:15 关闭，到了 17:25 仍可能用于学习，但不适合周期级实时控制。可以定义窗口年龄：

\[
a_{\mathrm{data}}=t_{\mathrm{decision}}-t_{\mathrm{window\ end}}
\]

若数据年龄超过该控制层级的阈值，置信度即使为 1.0 也不能自动下发。置信度回答“这个值本身有多可靠”，新鲜度回答“它是否仍代表当前世界”，两者不能互相替代。

关键阶段和非关键阶段也可以有不同阈值。东直关键阶段缺失时，系统可能应保持原方案；一个右转低流量流向的短时缺失，或许只影响报告，不影响主阶段绿时。差异需要有显式配置和风险审查依据，不能由算法临时猜测。

这个门控在当前实现里有一个前置缺口：生产链路的 `Confidence` 恒为默认值 `1`（第 25.10 节），所以“低置信度”这个条件无法成立。门控代码即使写了，也等于只检查设备状态和方案合法性。要真正启用数据质量门控，需要先让质量字段从 Flink 一路带到算法输入，并给出可核验的来源。

## 14.5 方案无效

方案校验失败时，可能的处置顺序为：

1. 尝试修复最小绿或整数舍入。
2. 使用同相序安全候选。
3. 保持当前已验证方案。
4. 回退到设备安全模式。

不能修复的错误，如冲突相位、未知关键阶段或周期无法闭合，不允许通过降低得分继续使用。

### 14.5.1 修复顺序与不可修复错误

可以把方案错误分成三类：

具体见表 14-3。
表 14-3 修复顺序与不可修复错误
| 类型 | 例子 | 可接受处置 |
|---|---|---|
| 表示误差 | 百分比转整数少 1 秒 | 确定性取整并重新校验 |
| 可修补约束 | 某阶段低于最小绿但其他阶段有余量 | 最小绿修复并再次验证 |
| 结构错误 | 冲突相位、未知阶段、周期依赖循环 | 拒绝，保持原方案 |

修复函数只能处理明确的第二类情况。它不能把冲突相位通过“少放行一个流向”自动改成另一个业务方案，也不能删除未知阶段续跑。自动修复的每一步都应记录 `repair_type`、输入、输出和验证结果。

修复后的方案是一个新版本。它不能沿用修复前的方案 ID 和审核状态，否则旧的测试证据会被错误地关联到不同内容。

## 14.6 下发失败与部分成功

子区批量下发可能出现部分成功。系统至少需要记录：

- 哪些路口成功
- 哪些路口拒绝或超时
- 已成功路口是否应回滚
- 回滚是否完整
- 子区是否暂时失去协调

只返回 HTTP 成功不代表全部设备执行成功。命令状态和运行状态需要分开。

### 14.6.1 部分失败的协调决策

假设 S1、S2、S3 已观察新方案，S4 仍运行旧方案。此时协调链不再完整。系统可以在若干策略中选择：

```text
policy A: rollback all to prior coordinated plan
policy B: retry S4 and hold others
policy C: detach S4 and run S1-S3 as new subgroup
policy D: recompute coordination around observed states
```

选择策略需要目标函数和硬约束。回滚最一致，但可能让三个已成功路口再次切换；保持部分成功可能让 S4 与 S3 的绿窗错位；重新计算可能需要新方案版本和人工审核；把失败路口拆出协调组，会改变子区结构，影响管理边界。

一个可解释的决策过程是：

1. 判断 S4 是否能在一个安全窗口内恢复。
2. 判断新协调方案是否存在设备已验证的公共周期。
3. 比较回滚与部分运行的风险，而不是只比较平均延误。
4. 记录选择理由和责任人。
5. 恢复后重新建立统一批次和版本。

批量命令状态不是“成功数 / 总数”这么简单，协调拓扑和路口重要性可能改变最优处置。

## 14.7 回滚

回滚目标应是一个已知版本，不是“上次用过的参数”这种模糊引用。

回滚前检查：

- 旧方案仍有效且设备支持
- 旧方案没有引用已删除阶段
- 当前路口拓扑和渠道没有变化
- 相位差仍与相邻路口兼容

回滚本身也可能失败，因此需要独立的命令状态和告警。

### 回滚后的确认

回滚完成不应只看“发送成功”。需要确认：

- 设备当前方案版本已恢复
- 周期和阶段与旧方案一致
- 控制模式恢复为预期模式
- 失败路口没有再次拒绝命令
- 子区其他路口与回滚后基准保持兼容

如果旧方案本身已经不再有效，系统应进入安全固定方案或现场接管，而不是强行恢复失效配置。

### 14.7.1 回滚的目标版本解析

回滚请求如果只写 `target=previous`，在不同操作者、不同重试时间下可能解析成不同方案。应保存明确的版本：

```text
rollback_to_plan_version
rollback_to_offset_version
rollback_to_schedule_version
rollback_reason
rollback_requested_by
rollback_deadline
```

如果旧方案引用的阶段已被删除，系统不能直接从历史 JSON 重新创建一份与当前设备不兼容的配置。历史方案应保留不可变的方案快照和设备能力快照，或者明确标记不可直接回滚。

回滚后的运行确认需要检查：

```text
observed plan version == rollback target
cycle == target cycle
stage sequence == target sequence
control mode is compatible
state age <= freshness threshold
```

确认通过后，回滚命令进入 `observed`；设备拒绝则记录失败原因；状态不一致则进入人工核查。不能把“回滚命令已发送”展示成“系统已恢复”。

## 14.8 本章实验

1. 分别让设备离线、状态过期、输入置信度低，观察不同拒绝原因。
2. 设计一个降级函数，根据故障严重度返回允许操作。
3. 模拟三个路口批量下发，两成功一失败，定义回滚策略。
4. 设计恢复流程，要求先同步设备状态再恢复自动控制。
5. 构造设备离线、低置信度和方案未校验同时发生的请求，按优先级输出唯一降级状态。
6. 设计 S1/S2 正常、S3 只推荐、S4 离线的子区方案，比较保持、把失败路口拆出协调组和重新协调三种策略的风险。
7. 让回滚目标方案的阶段配置已被删除，验证系统拒绝自动回滚并进入安全模式。

## 14.9 小结

这一章把“自动化能不能继续”写成一条有优先级的判断链：设备离线、数据过期、方案无效、下发失败与部分成功，各自有明确的降级等级和恢复条件；回滚不是“再发一次”，而是目标版本、依赖版本和完成条件都要能对上。安全降级的核心是明确自动化能做什么、不能做什么——每个故障映射到可解释状态，每次下发都能追踪、重试、确认和回滚。

单个路口的门控和降级走到这里，问题自然往路口之间走：一个路口可以降级，一条干道也要有同样的判断；相邻路口的周期、相位差和子区边界需要一起决定。下一章把控制问题从单个路口推向路口之间，先讨论子区怎么划、哪些路口可以协调。

## 第三部分评点：结构先于算法

配时算法很容易给人一种错觉：只要目标函数足够好，周期和绿信比自然会算对。

但信号控制不是一张可以任意涂改的白纸。相位决定哪些流向能同时放行，阶段决定许可集合，清空时间决定黄灯和全红，最小绿决定行人有没有时间过街。这些结构一旦错了，后面的优化越漂亮，错得越远。

所以这一部分先讲相位、阶段、环和屏障，再讲周期、绿信比和 Webster，最后讲自适应和安全门控。顺序不是随意的：先确定“允许做什么”，再讨论“怎样做得更好”。安全约束也不是算法算完之后补一层检查，它从结构开始就在场。

工程上最难接受的，不是方案指标不够漂亮，而是指标很漂亮、现场却不能用。指标好而现场不能用，通常不是现场保守，而是模型从一开始就没有把结构约束当回事。

先确定允许做什么，再讨论怎样做得更好——这个顺序，比任何一组优化参数都更靠前。

## 练习

1. 设备恢复在线后为什么不能立即判定自动方案生效？
2. 低置信度输入适合完全禁止控制算法吗？请区分推荐和自动执行。
3. 批量下发部分失败有哪些可能的处置方式？
4. 为回滚目标设计版本检查清单。
5. 为什么“设备已恢复连接”不能直接等同于“可以恢复自动控制”？
6. 证明一个包含冲突相位的方案即使能通过周期校验，也不能通过完整安全门控。
7. 说明部分路口失败时，为什么批量成功率不能作为唯一恢复依据。
8. 设计一个故障事件表，使每次自动降级和人工恢复都能追溯到证据与决定。

## 本章工程自查

在把自动控制接入真实路口前，逐项回答以下问题：

具体见表 14-4。
表 14-4 本章工程自查
| 检查项 | 需要给出的证据 |
|---|---|
| 方案来源 | 方案 ID、版本和审核记录 |
| 相序兼容 | 与当前方案的阶段序列比较结果 |
| 周期与最小绿 | 完整时间轴校验结果 |
| 数据状态 | 观测时间、完整性和置信度 |
| 设备状态 | 在线状态、控制模式和最近心跳 |
| 命令标识 | commandId、batchId 和幂等策略 |
| 执行确认 | 实时方案、周期和阶段的匹配证据 |
| 恢复路径 | 已验证的回滚版本或安全模式 |

没有证据的项目应按“未满足”处理，而不是按默认值通过。自动控制的价值来自持续工作，安全价值来自在条件不充分时拒绝继续。

一个推荐的发布流程是：

```text
离线方案测试
  -> 设备能力验证
  -> 小范围人工确认
  -> 监控模式试运行
  -> 有限自动控制
  -> 正常运行与周期复审
```

每一步都应记录退出条件和责任人。系统不应因为某一次试运行没有事故，就自动扩大自动化范围。
