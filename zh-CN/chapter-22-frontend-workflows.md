# 第 22 章 前端工作流与运行监控

第 21 章的命令状态机回答了“平台让路口发生了什么、每一步有没有记录”；本章把这些记录如实呈现给操作者——这是前端工作流的话题。信号控制前端把人和操作流程串起来：方案库、调度、算法推荐、自动控制、任务和评价经由它连成一个流程，操作者的每个决定都从这里出发。第 19 章立起的服务边界在页面上再现：页面展示的每一类数据，都来自边界某一侧的服务。

阅读本章前，第 19 章的服务边界与第 21 章的命令生命周期应已在手边，轮询与状态管理等基本前端概念是本章的外部技能；本章对应的生产实现见第 28 章。

WaySense 前端中的 RD 模块包括：

- 基础信号控制
- 路口方案库
- 子区方案库
- 信控调度库
- 智能方案推荐
- 智能方案计算
- AI 自动控制
- 分区管理
- 任务管理
- 信号控制评价
- 调控日志

前端的核心任务是帮助用户回答四个问题：我看到的对象是谁，当前数据来自什么时候，方案处于哪个生命周期，下一步操作会改变什么。一个页面如果只展示“当前周期 92 秒”，却没有说明它是目标方案、调度计划还是设备观测，就会制造虚假的确定性。

本章围绕 S2 17:00 换方案，设计从推荐到执行、监控、评价与审计的界面状态。

## 22.1 方案库

方案库用于查看和编辑可复用方案。页面需要呈现：

- 周期
- 阶段顺序
- 每阶段时长
- 关键阶段
- 相位差
- 使用状态和版本

编辑时需要即时校验周期总和、最小绿和相序兼容。

### 22.1.1 编辑器的领域约束

方案编辑器不能只把阶段秒数提交给后端。它至少需要在本地显示：

```text
sum(stage durations)
cycle
pure green total
clearance total
minimum green violations
stage sequence
referenced offset plan
plan version
```

假设用户把 A 阶段从 30 秒改为 35 秒。编辑器可以立即显示周期多出 5 秒，但不能自动悄悄把 B 阶段减 5 秒。自动修复会改变另一个交通工程师刚编辑的方向，而且可能触发最小绿。更好的交互是显示冲突、提供明确的分配操作，并把最终修改记录为一次版本变更。

方案库中的“保存”与“发布”需要分开。保存草稿可以允许暂时不完整，发布需要通过完整校验。把草稿的黄色警告显示成可执行方案，会让用户误以为它已经可用。

### 22.1.2 版本和并发编辑

两个用户同时编辑 `S2 v41` 时，后保存者可能覆盖前者。编辑器打开时应记录 `expectedVersion`，保存请求携带它。后端条件更新失败后，页面显示“方案已被其他人修改”，并提供重新加载或比较差异，不能直接重试覆盖。

变更摘要应显示：

```text
field
old value
new value
unit
changed by
changed at
```

交通工程师需要比较的是阶段时间差异，而不是一整段 JSON diff。

## 22.2 推荐与计算

推荐页面展示算法生成的路口和子区方案；计算页面允许调整时段、协调方向、关键路口和牺牲参数。

前端不能只显示最终秒数，还应展示：

- 原方案与推荐方案差异
- 使用的流量窗口
- 关键路口和协调方向
- 警告与不可行原因
- 算法版本

### 22.2.1 推荐差异需要可解释

推荐页面至少并列显示原方案和推荐方案：

具体见表 22-1。
表 22-1 推荐差异需要可解释
| 字段 | 原方案 | 推荐 | 差异 |
|---|---:|---:|---:|
| 周期 | 88 s | 92 s | +4 s |
| A 阶段纯绿 | 28 s | 31 s | +3 s |
| B 阶段纯绿 | 21 s | 20 s | -1 s |
| C 阶段纯绿 | 17 s | 17 s | 0 |
| 关键阶段 | B | B | 不变 |
| 相序 | A-B-C | A-B-C | 兼容 |

用户还应看到关键流量比、输入窗口、数据完整率、设备约束和未解决警告。一个推荐方案即使周期更高，也可能因为高峰需求需要更大容量；不能只按周期大小判断好坏。

### 22.2.2 计算任务与结果版本

点击“计算”后，页面可以发起长任务，但不应该把按钮点击当作成功。任务至少保存：

```text
task_id
request_id
state
submitted_at
started_at
finished_at
input_versions
result_id
error_code
```

用户切换路口或刷新页面后，任务仍应按 `task_id` 查询结果。旧请求晚到不能覆盖新路口的详情。页面应使用请求令牌或实体版本忽略过期响应。

### 请求状态

计算页面至少需要区分：

```text
idle
loading
success
partial
infeasible
error
```

成功但带警告与完全成功不同；算法不可行也不等于网络错误。界面应保留原方案和输入参数，允许用户修改约束后重试。

### 22.2.3 错误和不可行状态

`infeasible` 不是空白。页面应显示：

- 哪个约束不可满足；
- 哪个阶段或流向造成问题；
- 输入是否可信；
- 可以调整哪些参数；
- 是否有安全候选可查看。

如果是 `request_timeout`，页面应显示任务可能仍在运行，并提供查询；如果是 `input_stale`，应提示重新获取流量；如果是 `permission_denied`，不能引导用户重复点击。错误语义决定交互动作。

## 22.3 自动控制

自动控制页面连接：

- 实时控制模式
- 当前周期和阶段
- 方案执行日志
- 设备状态
- 评价曲线和时空图

用户需要在同一上下文中判断“为什么切换”“切换后发生了什么”“是否需要人工接管”。

### 22.3.1 一个路口详情的数据快照

详情页可以组合：

```json
{
  "siteId": "site-S2",
  "targetPlan": {"version": "v42", "cycle": 92},
  "scheduledAt": "17:00:00+08:00",
  "command": {"batchId": "b-1700", "status": "dispatched"},
  "observed": {
    "planVersion": "v41",
    "cycle": 88,
    "stage": "B",
    "observedAt": "17:00:05+08:00"
  },
  "dataQuality": {"complete": false, "reason": "E2 missing"}
}
```

页面应把这段状态解释为“目标 v42，命令已发送但设备仍观测到 v41，执行待确认”，而不是简单显示 `currentPlan=v42`。`observedAt` 和页面生成时间需要一起展示，避免用户把五分钟前快照当成现在。

### 22.3.2 刷新时钟

设页面刷新周期为 \(T_r\)，设备状态上报周期为 \(T_s\)，则页面最多可能看到约 \(T_r+T_s\) 秒前的状态。这个延迟不是 UI bug，但如果界面把每一轮响应都写成 `实时`，用户会低估状态年龄。

前端显示：

```text
device_time
received_at
view_refreshed_at
state_age
```

当状态年龄超过阈值时，黄色或灰色应明确表示“数据过期”，不能继续使用绿色“在线”。颜色只是辅助，文字和图标需要能独立表达状态。

当前 `AutoControlSite` 使用 120 秒定时器。定时回调调用 `this.refresh(...)` 后没有等待它完成，紧接着 `await this.getDetailInfo()`。如果全局刷新本身是异步 action，前后两轮请求可以重叠。生产页面需要单飞（single-flight）控制，并把当前 `siteId` 和请求序号写入响应准入条件。

### 地图和列表的一致性

地图、列表和详情通常使用不同接口。点击一个路口后，地图高亮、列表选中和详情数据需要引用同一实体 ID 和同一刷新版本。否则用户可能在地图上看到 A，却在详情中读到 B。

前端状态可以分成：

```text
selected entity
loaded snapshot
pending request
last refresh time
```

四次异步响应返回顺序不同，不能依赖请求完成顺序更新界面。

### 22.3.2.1 页面是多个事实视图的组合

自动控制页面至少合并四类事实：

\[
V=(T,Q,O,D)
\]

其中 \(T\) 是目标方案，\(Q\) 是命令状态，\(O\) 是设备观测，\(D\) 是数据质量。四类事实由不同服务产生，拥有不同版本和时间。页面不能用其中的 \(T\) 替代 \(O\)，也不能把最后到达的响应当作最新事实。

一个响应可以写成：

\[
R_i=(e_i,r_i,s_i,a_i)
\]

分别表示实体、请求序号、业务版本和观测时间。只有同时满足：

\[
e_i=e_{\mathrm{selected}}
\land r_i\ge r_{\mathrm{displayed}}
\land a_i\ge a_{\mathrm{displayed}}
\]

才允许更新当前详情。不同服务的时间字段语义不同，页面应分别比较实体版本和事件时间，而不是一律比较浏览器收到响应的时间。

这组规则解释了为什么前端的乐观更新需要受限。编辑草稿时可以在本地显示未保存值，但设备观测、命令确认和评价结果不能因为用户点击按钮而乐观变成成功。页面可以显示“正在发送”，却需要等待服务端事件和观测证据才能显示“已生效”。

加载失败也不等于对象不存在。网络错误、权限不足、超时和服务端空结果需要分别呈现。一个统一的空状态会把系统故障伪装成“没有方案”，让用户做出错误操作。

### 22.3.3 竞态与取消

用户从 S2 切到 S3，再切回 S2，可能同时有三次详情请求。即使 S3 请求最后返回，也不能覆盖当前选中的 S2。前端可以使用：

```text
selected_id + request_sequence
```

只有响应中的实体与当前选中实体一致且请求序不旧于已显示版本时才更新数据。React、Vue 或别的框架，其组件生命周期也不能自动解决这个业务竞态。

长计算任务应支持取消本地等待，但服务端任务是否取消是另一层状态。用户不需要看到实现细节，页面至少要区分“本地不再等待”和“服务端已取消”。

## 22.4 状态一致性

前端可能同时看到：

- 方案库中的目标方案
- 调度中的下一条命令
- 设备当前方案
- 实时周期

它们属于不同状态。页面需要明确标识，不能把方案库中的方案直接写成“正在执行”。

一个可操作的页面应同时显示：

具体见表 22-2。
表 22-2 状态一致性
| 面板 | 回答的问题 |
|---|---|
| 目标方案 | 我们希望执行什么 |
| 调度记录 | 计划何时执行 |
| 命令状态 | 是否已发送和接受 |
| 实时状态 | 设备正在执行什么 |
| 控制评价 | 执行后发生了什么 |

自动控制页面还应有“最后一次刷新时间”。WaySense 前端把部分自动控制刷新周期配置为 120 秒，因此页面上的实时状态仍可能在两次刷新之间过期。界面应显示数据时间，而不是把旧数据渲染成当前值。

### 22.4.1 五个状态面板的证据

每个面板都应有一个权威来源：

具体见表 22-3。
表 22-3 五个状态面板的证据
| 面板 | 权威来源 | 主要错误 |
|---|---|---|
| 目标方案 | 方案库发布版本 | 展示草稿或旧版本 |
| 调度记录 | 调度服务 | 把未到时间当成已执行 |
| 命令状态 | 命令服务/设备网关 | 接受与观测混用 |
| 实时状态 | 设备适配器事件 | 过期、未知模式 |
| 控制评价 | 评价任务 | 把相关变化当因果 |

当五个面板不一致时，界面不应选择一个“看起来最正常”的值自动统一。它应显示冲突并给出时间、版本和来源，让用户知道系统内部确实不一致。

### 22.4.2 不可操作状态

按钮应基于门控结果禁用，并给出原因：

```text
disabled: plan version conflict
disabled: device offline
disabled: telemetry stale
disabled: user lacks dispatch permission
disabled: selected plan is draft
```

只把按钮变灰不说明原因，用户会反复刷新或联系支持。禁用原因需要来自后端或与后端相同的规则，不能由前端本地猜测后造成误操作。

### 22.4.3 三种刷新策略

前端拿到“实时状态”有三种方式：

具体见表 22-4。
表 22-4 三种刷新策略
| 策略 | 延迟 | 服务端压力 | 竞态风险 | 实现复杂度 |
|---|---|---|---|---|
| 轮询 | 等于轮询周期 | 与页面数成正比 | 旧响应可能覆盖新响应 | 低 |
| WebSocket 推送 | 秒级以内 | 长连接管理 | 重连期间状态丢失 | 中 |
| 事件流订阅 | 秒级以内，可回放 | 需要消费端游标 | 顺序与重复处理 | 高 |

WaySense 的自动控制页面采用 120 秒轮询，并且没有请求取消：用户在两个实体之间快速切换时，先发出的请求可能后返回，把旧实体的数据写到新页面上。问题不在轮询本身；轮询要配三件事：请求序号（只接受最新一次）、取消或忽略过期响应、页面显示数据时间。

推送和事件流也不是免费升级：它们把复杂度从“定时器”转移到“连接、重连、鉴权和游标”。在没有服务端推送能力之前，正确做法是把轮询做对，而不是假装实时。

## 22.5 操作权限

查看、计算、保存、审核和下发是不同权限。权限系统需要覆盖：

- 菜单可见性
- API 调用
- 数据范围
- 操作审批
- 日志追踪

前端隐藏按钮不能代替后端权限校验。

### 22.5.1 权限与数据范围

权限至少分三层：

1. 功能权限：能否查看推荐、保存、审核、下发、回滚。
2. 数据范围：能操作哪些路口或子区。
3. 操作条件：当前故障、时间窗口、审批状态是否允许。

用户有 `dispatch` 权限，不代表能下发一个未审核方案；用户有路口范围，不代表能操作子区协调批次。后端需要重新计算这些条件。

### 22.5.2 二阶段操作的内容绑定

确认弹窗应绑定具体命令摘要：

```text
target sites
plan versions
current vs target cycle
effective time
expected coordination group
validation result
irreversible risks
```

用户在确认前切换到另一个方案，旧弹窗不能继续有效。确认令牌应包含方案版本和目标时间，提交时由后端再次校验。

### 二阶段操作

下发和回滚属于高影响操作。界面可以让用户先查看：

- 目标路口和设备
- 目标方案版本
- 当前方案和差异
- 预计生效时间
- 约束检查和警告

确认后再生成命令。确认步骤需要绑定具体命令内容，不能是缓存的“允许任意操作”状态。

## 22.6 调控日志

日志至少应回答：

- 谁发起了操作
- 针对哪个路口和方案版本
- 是人工还是自动
- 何时下发
- 设备是否接受
- 实际何时生效
- 是否回滚

日志是运行检查和安全审查的主要证据。

日志查询还应支持：

- 按路口、批次、方案版本和时间检索
- 查看命令与实时状态的对应关系
- 导出失败原因和回滚结果
- 区分人工操作、自动推荐和基础调度

日志数据不应被后续方案编辑覆盖。它记录的是当时发生的事实，不是当前配置的投影。

### 22.6.1 日志与指标的边界

调控日志记录操作事实，如“谁在何时请求下发 v42、设备回复什么”；控制评价记录运行效果，如“速度、饱和度和排队在窗口内如何变化”。两者可以关联，但不能把日志成功当效果成功。

日志需要保留失败尝试。失败的命令被删除后，系统将无法解释为什么某个路口曾经没有切换，也无法训练和改进运维流程。对敏感字段进行脱敏，但不删除操作事实。

### 22.6.2 事故分析视图

一次事故分析至少能按时间轴展开：

```text
17:00:00 target v42 created
17:00:02 command dispatched
17:00:03 S1 accepted
17:00:05 S2 observed v41
17:00:30 S2 still v41
17:01:10 operator opens incident
17:02:00 rollback issued
17:02:30 S2 observed v41 rollback target
```

每个事件都带来源、版本、操作者和原始状态摘要。分析页面不应只画一条“系统故障”红线，而要让工程师看到状态在哪一步分叉。

## 22.7 本章实验

1. 画出从推荐到调度、下发、运行的页面状态流。
2. 为“方案已保存”和“方案已生效”设计不同视觉状态。
3. 为一个操作设计权限和审计记录。
4. 把实时周期和方案库周期放在同一页面，要求标注来源。

### 页面状态设计

构造以下状态：

```text
方案库：方案 v12
调度：计划 09:00 使用 v12
命令：09:00:02 已发送
设备：当前仍是 v11
实时阶段：09:00:10 属于 v11
```

页面应显示“下发中或执行未确认”，不能显示“v12 正在执行”。这个例子体现了目标状态、命令状态和观测状态之间的差异。

再构造一个前端竞态：

```text
17:00:01 click S2 -> request A
17:00:02 click S3 -> request B
17:00:03 click S2 -> request C
17:00:04 B returns S3
17:00:05 A returns old S2
17:00:06 C returns current S2
```

如果按响应顺序更新，最后可能显示旧 S2；如果只按当前选中 S2 判断，A 和 C 都可能通过，仍需请求序列。页面应最终展示 C 的数据，并把 A 识别为过期响应。

### 22.7.1 可访问和可操作的状态

状态不能只靠颜色区分。在线、离线、未知、过期应有文字、形状或图标；图表应有数值表和文本摘要；关键数字要带单位和数据时间。对屏幕阅读器和色觉受限用户，颜色不是唯一信息来源。

表格用于比较目标、命令、观测和评价时，应提供可复制的文本摘要。运营人员需要在交接和事故记录中引用具体状态，而不是只能截图。

## 22.8 小结

前端是系统状态的解释界面。它需要连接领域模型、算法结果、命令状态和设备状态，同时避免把不同层次的数据混成同一个“当前方案”——本章的五个状态面板、请求准入条件和竞态防护，都是为了让页面上的每个数字都带着自己的来源、版本和时间。

页面把执行记录展示出来之后，接下来要看执行之后交通发生了什么。第 23 章的控制效果评价要在同一时间框架里比较需求、方案、设备状态和运行结果，把“执行了”与“改善了”分开证明——那正是 22.6.1 节日志与指标边界留下的伏笔。

## 第五部分评点：命令层是风险最高的地方

算法错了，最坏的结果是给出一个差方案；命令错了，最坏的结果是把错误方案送进真实路口。

这一部分从 Java 与 Python 的边界，一直讲到 Kafka、Flink、批量下发、部分成功和前端状态。看起来是软件工程，其实每一节都在回答同一个问题：控制意图怎样安全地变成设备事实。

这里最容易混淆的是“成功”。接口返回成功，只说明请求被受理；设备 ACK，只说明命令被收到；运行状态确认，才说明方案真的在跑。三层证据混成一句“已下发”，事故分析就会失去方向。

前端也不是“画页面”。它要把目标、命令、运行事实和评价放在同一个时间轴上，让值班人员知道现在看到的是计划、是命令，还是设备正在执行的状态。

所以这一部分反复追问的不是“发下去没有”，而是“哪一层确认了”。只有把请求、命令和运行状态这三层证据分开，值班人员看到的才不是一句“成功”，而是一条可追的责任链。
